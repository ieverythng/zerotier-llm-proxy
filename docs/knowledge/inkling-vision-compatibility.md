# Inkling 2 Mini Mix-12G: native vision compatibility

**Verdict (2026-11-25):** The **installed and configured** OrcaRouter abliterated Mix-12G is text-only. It retains the right text-backbone shape and image markers to make the official **Inkling 2 Mini** projector a credible test candidate. Neither the artifacts examined nor a matching width establish that the **exact** cross-publisher pair processes pixels correctly. Keep the current aliases text-only until an isolated image-dependent test passes. No weights/projector were downloaded, no model was run, and no Watson model, Saluki, or DSH settings were changed.

## What is actually installed

It is **11,634,058,560 bytes**, GGUF **v3**, `general.name = Inkling-2-Mini-abliterated`, `general.architecture = inkling2_loop`, **704** tensor descriptors, **62** metadata entries, **24** blocks, **3** loops, and input embedding width **2,304** (`token_embd.weight` is `[2304, 201024]` in GGUF dimension order). Tensor name families were only `blk`, `output`, `output_norm`, `output_res_query`, `token_embd`, and `token_embd_norm`; there is no separate vision tower/projector tensor family in this file.

The template's image branch renders the wrapper and placeholder. Those tokens are **not** an encoder; seeing a template accept an image slot, or generating a plausible answer, is not evidence that pixels reached the decoder.

## Which projector makes technical sense?

Thinking Machines Lab's [base model card at `c9d02830…`](https://huggingface.co/thinkingmachines/Inkling-2-Mini/blob/c9d028302cd0f035fdf8e7e91f089a4ce94d2195/README.md#3-model-properties) documents native **image + text → text** through a ViT and a shared decoder space. Its [pinned configuration](https://huggingface.co/thinkingmachines/Inkling-2-Mini/raw/c9d028302cd0f035fdf8e7e91f089a4ce94d2195/config.json) gives vision width **1,024**, **23** vision layers, **20**-pixel native patches, **2** spatial merge, projection hidden size **4,096**, and projection to text width **2,304**. The original's multimodal capability does not imply the local text GGUF embeds that encoder.

The [ggml-org conversion card at `e8a2cecf…`](https://huggingface.co/ggml-org/Inkling-2-Mini-GGUF/raw/e8a2cecf0e78914f07cc27b9be711a9b2c7561d9/README.md) ships the **matching base model’s encoder and projector together as a separate `mmproj`**. Its [pinned tree](https://huggingface.co/api/models/ggml-org/Inkling-2-Mini-GGUF/tree/e8a2cecf0e78914f07cc27b9be711a9b2c7561d9) gives these artifact identities (file sizes, **not runtime VRAM**):

| Official Mini projector | Bytes | Published LFS SHA-256 |
| --- | ---: | --- |
| [`mmproj-Inkling-2-Mini-Q8_0.gguf`](https://huggingface.co/ggml-org/Inkling-2-Mini-GGUF/blob/e8a2cecf0e78914f07cc27b9be711a9b2c7561d9/mmproj-Inkling-2-Mini-Q8_0.gguf) | 345,910,944 (~330 MiB) | `233287272ec5ac39b4168677aba54a4c024f202410f5629fac1830e1059f8abb` |
| [`mmproj-Inkling-2-Mini-BF16.gguf`](https://huggingface.co/ggml-org/Inkling-2-Mini-GGUF/blob/e8a2cecf0e78914f07cc27b9be711a9b2c7561d9/mmproj-Inkling-2-Mini-BF16.gguf) | 641,805,984 (~612 MiB) | `e914997fe07fb2066bfdce855ec7275c15bc2b624e5423149f1027839593d9cb` |

Q8_0 is the smaller first candidate **if a later test is approved**; its quantization applies to the vision side, and it does not have to match the text quantization label. The least bulky decoder in this particular official conversion tree, IQ4_NL, already occupies **17,627,940,768 bytes (~16.42 GiB) on disk** before the projector; do not infer an all-GPU fit on a nominal 16-GiB card from the official recipe. Neither projector's binary header, actual peak memory, quality, nor behavior with this local Mix-12G was tested here.

There is a useful but bounded precedent. [mrfakename's pinned abliterated variant `686fa052…`](https://huggingface.co/mrfakename/Inkling-2-Mini-abliterated-GGUF/raw/686fa052107b25ef0c636d3897eb82a915db2fbb/README.md) explicitly pairs **its own Q8_0 decoder** with the unchanged ggml-org Mini Q8_0 projector; the [pinned artifact tree](https://huggingface.co/api/models/mrfakename/Inkling-2-Mini-abliterated-GGUF/tree/686fa052107b25ef0c636d3897eb82a915db2fbb) gives identical LFS hashes for both projectors. This shows that one documented ablation can reuse base vision weights; that decoder is **not** OrcaRouter's Mix-12G, and the comparison does not prove its visual quality or compatibility. No release or first-party test was found that explicitly qualifies the exact Mix-12G plus official Mini projector combination.

## What the pinned runtime verifies, and what it does not

- Upstream introduced [Inkling 2 text and vision](https://github.com/ggml-org/llama.cpp/pull/32217) and then the [Mini looped implementation](https://github.com/ggml-org/llama.cpp/pull/32694). The short-profile [b12633 source](https://github.com/ggml-org/llama.cpp/blob/9c10c94e16ebc4f3ed7c06264a93bf7e019c3f26/tools/mtmd/models/inkling2v.cpp) and the long-profile [b12651 source](https://github.com/ggml-org/llama.cpp/blob/f5e6915c28f10330885fcb9243a93ae98d3115ab/tools/mtmd/models/inkling2v.cpp) both contain the Inkling2V graph: ViT, patch merging, and two-layer projection into the model input space. The local tracked source for the long pin was at `f5e6915c28f10330885fcb9243a93ae98d3115ab` and had no modifications in the inspected converter/mtmd paths. The [b12651 CLI source](https://github.com/ggml-org/llama.cpp/blob/f5e6915c28f10330885fcb9243a93ae98d3115ab/common/arg.cpp#L2552-L2619) declares `--mmproj` (`-mm`), `--mmproj-offload` / `--no-mmproj-offload`, and image-token bounds. Source support is not proof that the installed binaries have successfully loaded the pair.
- The [b12651 converter](https://github.com/ggml-org/llama.cpp/blob/f5e6915c28f10330885fcb9243a93ae98d3115ab/conversion/inkling2.py#L332-L377) registers a separate `MmprojModel` for `Inkling2LoopForConditionalGeneration`, selects `inkling2v`, and maps the vision tower and projector tensors. The [language converter](https://github.com/ggml-org/llama.cpp/blob/f5e6915c28f10330885fcb9243a93ae98d3115ab/conversion/inkling2.py#L185-L195) omits vision and MTP. Omission from the text GGUF is exactly what a split GGUF architecture allows; absence of the MTP drafter is independent of attaching a projector.
- [mtmd startup](https://github.com/ggml-org/llama.cpp/blob/f5e6915c28f10330885fcb9243a93ae98d3115ab/tools/mtmd/mtmd.cpp#L1003-L1023) compares the projector embedding width and decoder input width and rejects a mismatch. The [Inkling2V media wrapper/preprocessor](https://github.com/ggml-org/llama.cpp/blob/f5e6915c28f10330885fcb9243a93ae98d3115ab/tools/mtmd/mtmd.cpp#L1146-L1151) uses `<|content_image|>`, consistent with the retained local marker. A size match and successful load still do not identify a projector's training pairing or check image-dependent grounding.

## Native vision versus a captioner or OCR

- **Native vision:** Image bytes → Mini ViT/projector → continuous image embeddings in Inkling's decoder input → text. The decoder can condition on pixels as well as text. An external `mmproj` is part of this native path; it is not another chat model. Matching input geometry, chat markers, capability declarations and resource limits all matter.
- **Captioner/OCR:** A separate, deliberately selected local image reader emits captions or text and Inkling receives only that text. It requires no Inkling projector and need not change what the existing aliases advertise. It loses any visual detail that was not transcribed (layout, diagrams, small labels, uncertainty), can introduce hallucinations, and requires treating its output as untrusted evidence, not instructions. It is an alternative integration, not proof of native image support. No captioner was selected, installed or tested here.
- **Later validation, not performed:** With approval, pin and verify the chosen projector bytes; inspect local GGUF metadata for `inkling2v` and the **2,304**-wide output; use an isolated lower-context profile on an owned idle worker, preserving normal resource reserves and both current aliases. Compare two different benign synthetic images containing withheld random IDs, and the same prompt with no image; require exact image-dependent answers and check small text/competing visual details before advertising images. Then verify unchanged text/tool behavior and approved inline-image traversal through the whole route, and measure memory/latency rather than budgeting only the projector's on-disk size. Do not send private attachments, reconfigure the live DSH picker, or substitute a Saluki/other-family projector for this experiment.
