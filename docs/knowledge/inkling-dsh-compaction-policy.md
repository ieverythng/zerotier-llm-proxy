# DSH Desktop: bound Inkling Long compaction separately from chat

**Scope:** installed Windows Desktop DSH and `@deepseek-ai/dsh-compaction-basic` **0.2.2-rc.5**. The first diagnosis below was of a different session: 17 HTTP 400 compaction errors across turns 13 and 14 even though both user turns completed. It did not capture the outgoing summary body. The 4,096-token override was subsequently installed and completed durable summaries. The newer incident is different: the gateway accepted the request, but the generated summary ran out of tokens. The section below records the distinction.

## Two separate failures in the later session

The exact watched session recorded a committed 4,096-cap compaction on turn 28, then seven truncations across turns 29–32. These attempts took **78–193 seconds**, far below the configured 20-minute I/O allowance. A truncation means DSH saw `max-tokens` and deliberately did not replace the conversation with an incomplete checkpoint. It is not the old HTTP 400 validation failure. A busy HTTP 409 was persisted **20–22 ms** after the last compaction failure in each of those turns (and after turn 27's older truncation). That timing is consistent with receiving stream termination before admission release. It does not prove that the decoder was still generating. A synthetic gateway test can distinguish that race from a truly busy worker without replaying a conversation.

The [installed 1.1.0 bundle](<../../plugins/watson-inkling-compaction-8192/README.md>) targets the exact Inkling Long route: **8,192 summary output tokens** under the unchanged 10,000 chat ceiling, unchanged pressure/headroom, 150,016 context, and native vision. Deterministic testing of the installed DSH resolver and summarizer reproduced `MAX_TOKENS` at 4,096 and a valid synthetic summary at 8,192. A benign live loopback summary accepted the 8,192 budget and ended naturally in 5.625 s (4,356 input / 404 output); it preserved both fixture facts. This checks live budget admission and summary quality on one small fixture, not a near-window replay or a durable replacement on the user's thread. A higher cap is margin, not a guarantee of natural completion. If truncation returns, verify the effective preset revision and output count before considering earlier or smaller compaction. Never store a truncated draft as a checkpoint. Separate HTTP 503 RAM reserve errors retain the existing guard.

The [Watson gateway](<../../local_stack/gateway.py#L369-L380>) now holds the SSE `[DONE]` event until upstream has closed, the backend is verified idle, and the admission lock is released. A malformed/unclosed stream emits an error rather than a false success. Tests reproduce the old 409 and verify the fix; a live synthetic stream ended with `length` at 64 tokens and a follow-up sent immediately at `[DONE]` completed without 409. This does not suppress legitimate busy errors or change the existing 20-minute timeout. Watson was gracefully reloaded while idle, and DSH was not restarted.

A hosted alternative is a separate, explicit preset, not a failover: DSH's summarizer transmits the selected history prefix and potentially tool schemas. Do not select it for sensitive or local-only work. A mounted Standard session keeps its old preset revision; a fresh Standard session, or an authorized genuine cold DSH resume, is required to pick up a new revision. Refreshing the UI alone is not sufficient. Do not restart DSH during active turns or use an unsupported in-place rebind.

## Why a valid chat cap does not fix summary requests

The [installed resolver, config.ts:68–109](<C:/Users/Admin/AppData/Local/Programs/DeepSeek Harness/resources/app.asar/dsh/node_modules/@deepseek-ai/dsh-compaction-basic/src/config.ts#L68-L109>) sets default compaction headroom to **65,536** and default summary `maxTokens` to that headroom. The [summary call, summarizer.ts:120–165](<C:/Users/Admin/AppData/Local/Programs/DeepSeek Harness/resources/app.asar/dsh/node_modules/@deepseek-ai/dsh-compaction-basic/src/summarizer.ts#L120-L165>) routes to the existing conversation model by default and explicitly puts this *separate* cap in its direct LLM request (`purpose: 'compaction'`). Updating the model's ordinary chat output cap is not a fix. If the active preset is using those defaults, **65,536 exceeds Watson's 10,000 output ceiling** and produces the deterministic output-budget HTTP 400 in [Watson gateway validation](<../../local_stack/gateway.py#L85-L93>). That is a source-backed hypothesis for the observed errors; do not claim the exact outgoing payload was captured. A failed summary can record `compaction/end` with an error without committing a replacement, and pressure-failure handling continues the turn ([region.ts:219–265](<C:/Users/Admin/AppData/Local/Programs/DeepSeek Harness/resources/app.asar/dsh/node_modules/@deepseek-ai/dsh-compaction-basic/src/region.ts#L219-L265>), [index.ts:157–175](<C:/Users/Admin/AppData/Local/Programs/DeepSeek Harness/resources/app.asar/dsh/node_modules/@deepseek-ai/dsh-compaction-basic/src/index.ts#L157-L175>)). Eligibility is recalculated before each agent step, not just once per user turn. `compactionRetries` counts additional convergence attempts after successful but insufficient reductions; reducing it does not correct the request or prevent a new failing attempt at the next step.

## Proposed exact route policy

Insert or update **one** model policy in the existing `compaction-basic` leaf configuration (preserve every other policy/field). Keep routing and retention options inherited; do not add an explicit different summary model. Both numbers matter: if `maxTokens` is omitted, it can inherit from explicit global policy or follow the headroom.

```yaml
# Leaf inside preset's compaction group; not a standalone profile patch.
- id: compaction-basic
  name: '@deepseek-ai/dsh-compaction-basic'
  config:
    modelPolicies:
      - provider: watson-local
        model: inkling2-mini-long
        headroomTokens: 8192
        maxTokens: 4096
```

This advertises neither a new chat context nor a lower ordinary chat cap. Route keys are exact `provider` and `model` strings, duplicates are rejected, and non-matching routes are unchanged. Ordinary pressure uses `floor(min(W × thresholdRatio, W − effective chat output reservation − headroomTokens))`; default retention is `floor((W − effective chat output reservation) × 0.16)`. This is DSH's priced trigger, not a guarantee about actual backend token counts. At the expected DSH context of **100,096**, an offline check of the installed resolver (Electron-as-Node, installed `config.ts` with Node's TypeScript stripping and the original shipped dependency) yielded:

| Policy | Chat output reservation | Pressure trigger | Retained tail budget | Summary cap |
| --- | ---: | ---: | ---: | ---: |
| Defaults | 4,096 | 30,464 | 15,360 | 65,536 |
| Defaults | 10,000 | 24,560 | 14,415 | 65,536 |
| Exact Inkling override | 4,096 | 80,076 | 15,360 | 4,096 |
| Exact Inkling override | 10,000 | 80,076 | 14,415 | 4,096 |

The same offline call confirmed `watson-local/saluki27b` retained the shipped defaults. For a smaller user-selected context, ensure `W − output reservation − 8192 > 0` and the retained budget is below the threshold. Neither the arithmetic nor HTTP admission qualifies summary quality at high pressure. Model switches evaluate pressure on the destination but ordinarily summarize with the previous durable route's policy, so the proposed override applies when Inkling Long is the conversation model being summarized, not to all summarizers ([resolver, config.ts:118–217](<C:/Users/Admin/AppData/Local/Programs/DeepSeek Harness/resources/app.asar/dsh/node_modules/@deepseek-ai/dsh-compaction-basic/src/config.ts#L118-L217>), [engine, index.ts:181–203](<C:/Users/Admin/AppData/Local/Programs/DeepSeek Harness/resources/app.asar/dsh/node_modules/@deepseek-ai/dsh-compaction-basic/src/index.ts#L181-L203>), [engine, index.ts:270–279](<C:/Users/Admin/AppData/Local/Programs/DeepSeek Harness/resources/app.asar/dsh/node_modules/@deepseek-ai/dsh-compaction-basic/src/index.ts#L270-L279>)).

## Validate and roll back only after approval

1. Inspect the current effective preset; preserve unrelated policy rows and the existing provider and model-picker settings. Do not change either default preset or default model for an isolated pilot. Verify the new declaration and its diagnostics before use.
2. Choose the updated preset before the first turn of a fresh, disposable session, use `watson-local/inkling2-mini-long`, and create a small balanced synthetic history. Run `/compact` **only in that test session** (it may persist a replacement); check `compaction/start`, an accepted summarizer request at **4,096**, a valid useful `compaction/summary` and replacement, and `compaction/end` without an error. Then send a second prompt and confirm it uses the checkpoint. `compaction/end` alone does not prove summary success. Also check the regular chat cap is unchanged. A manual pass does not prove automatic behavior near 80K; test that separately before qualification. Metadata-only checks are sufficient; do not log prompts, generated summaries, credentials, or raw tool data.
3. If it fails, stop the test, keep production provider settings and history unchanged, and disable/remove only the new bundle via the supported manager after the disposable session is released, or restore the exact prior declaration through that same workflow. A preset rollback does not undo successful replacements already committed to a tested session. Do not attempt repeated `/compact` in the user's real session to validate an unapplied policy.
